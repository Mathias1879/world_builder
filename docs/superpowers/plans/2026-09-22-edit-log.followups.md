# Edit Log — follow-ups

Items the final whole-branch review raised that are outside this branch's scope.

## For Editor [10] (browser persistence)

- **(a) Persist metadata, not just ops.** The editor stores each committed op as its own record, but branch heads/base, undo/redo stacks, versions, title and authors live only in `META`. Editor [10] must also persist that metadata as its own record (or as deltas) next to the per-op records. The alternative is a receive-without-merge mode in the crate. Today `apply_ops` always merges received ops into the *current* branch, so replaying stored ops alone can't rebuild other branches or the undo history.
- **(b) Batch `apply_ops`.** Each call re-materializes the current branch from the whole op graph. Callers should batch received ops into one call rather than applying them one at a time.

## Before co-editing

- **(c) Revisit undo semantics.** Undo writes back each field's value from *before* the undone op. With concurrent remote writes to the same field, that can overwrite a newer remote value. That's fine for a single user; co-editing needs a different rule (for example, skip fields whose current value no longer matches the undone op's write).
- **(d) Timeline flags.** `timeline()` marks the undone op as `undone`, but not the `Undo` op itself. UI that hides undo pairs will need to flag both.

## Deferred minors

- `add_asset` keeps the first `media_type` for identical bytes (first write wins); a later call with a different media type is ignored silently.
- `undo()`/`redo()` clone the whole target `Op` when they only need its writes and label.
- `restore_version` looks the version up twice (once in `view_version`, once for its name).
- The golden script has no `Int`, `Bool` or `List` values, so their encoding isn't covered by the cross-target gate.
- `EntityKind::reserved` is unused (it has an `#[allow(dead_code)]`).
- Style: the crate uses both `core::fmt` and `std` imports. Pick one convention.
